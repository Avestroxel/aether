# Performance as design constraint

Set budgets before choosing assets and effects: critical page JS/CSS, image weight, font requests and third-party scripts. Budgets depend on audience and network; measure a representative slow mobile device, not only a fast desktop. For field Core Web Vitals, aim at the 75th percentile for **LCP ≤ 2.5 s**, **INP ≤ 200 ms**, **CLS ≤ 0.1**. Lab runs and field data answer different questions; don't claim field success from a local Lighthouse run.

Prioritize the LCP element (often hero image or heading): compress and size it, serve responsive formats, preload only if it is genuinely critical, and do not lazy-load it. Specify image dimensions or aspect ratio to prevent shifts. Lazy-load below-fold images and non-critical 3D; use responsive `srcset`/`sizes`. Subset fonts, load only needed families/weights, and use resilient system fallbacks. Limit animation work on the main thread and avoid continuous rendering when idle. Prefer composited transforms/opacity where appropriate, reserve layout for pinned sections, avoid scroll handlers that force synchronous measurements every frame, and disconnect observers/timelines on teardown. Test jank and input latency while reversing scroll on representative low-powered devices; a smooth desktop capture is not evidence of mobile performance.

When evaluating a library, count shipped JS, hydration, network requests, runtime CPU/GPU, maintenance and accessibility impact—not just install size. Defer analytics/chat until they are needed and consented to where required. Run a before/after trace on the same route/device/network, then record the actual tradeoff. Prefer a simple CSS or static alternative when a heavy effect adds no task value.

# Self-improvement loop

Treat feedback as evidence, not a mandate to chase aesthetics. After each release or critique, compare the intended user task and success signal with observed behavior. Gather qualitative observations (task sessions, support tickets, accessibility reports) and quantitative signals (completion, error rate, performance), noting sample size, selection bias and confounders. Do not infer causation from a single metric shift.

Maintain a small decision log: **hypothesis → design choice → expected effect → measurement → outcome → next action**. Example: 'Visitors cannot compare plans; add a visible limits table; expect fewer pricing support questions; test five comparison tasks and track question volume; revise wording if questions persist.' Preserve the reasoning behind successful decisions and the failure modes of unsuccessful ones; don't canonize one-off aesthetic preferences as universal rules.

Prioritize issues by task impact, reach, severity and cost. Fix access blockers and incorrect content before polish. Change one major variable at a time when measuring impact; use an appropriate experiment or task test, then inspect guardrails (accessibility, latency, errors). In future work, retrieve only relevant lessons; re-test assumptions when audience, product or platform changes. Keep project-specific outcomes separate from reusable advice. Before submitting a lesson, remove secrets, personal data and private user feedback; verify source, permission and license for external material. `learn` stores local contributions for human review, not live instructions or model training. Promote a lesson only after checking evidence, applicability, accessibility/performance guardrails and conflicts with existing project rules. End a review with an owner, a next experiment and a clear stop condition rather than an open-ended redesign.

# Design thinking

Use as the entry lens for any new website, redesign, or product UI. Read [strategy](../../../aether/knowledge/strategy.md) and [category directions](../../../aether/knowledge/category-directions.md); use [improvement loop](../../../aether/knowledge/improvement-loop.md) when iterating on an existing implementation.

1. **Decode intent and category rapidly:** Extract the purpose, target audience, category archetype, visual personality, and primary user action from the prompt and repository. Distinguish between an **existing codebase with real product data** (preserve verified facts and domain constraints) and a **greenfield build from a short prompt** (commit to a rich, domain-authentic creative direction with concrete, realistic content). Ask clarifying questions only if a critical requirement is genuinely ambiguous and blocking.
2. **Compare two structural + aesthetic concepts silently:** Before writing code, mentally contrast at least two distinct structural and art-direction approaches (e.g., an asymmetric architectural monograph with indexical project specs vs. an immersive full-bleed spatial showcase; or a live interactive workflow theater vs. an editorial technical narrative). Select the direction with stronger category fit, clearer task hierarchy, and higher visual distinction.
3. **Map the narrative and spatial arc:** Order the journey from **hook → proof/experience → action → resolution**. Assign each viewport a distinct job and structural layout so sections build rhythm rather than repeating identical card grids. Add motion, scroll choreography, or 3D only when they sharpen narrative, spatial understanding, or state feedback; keep controls immediate and accessible.
4. **Execute directly in production UI code:** When asked to build, design, or redesign a website or interface, **immediately express your chosen creative direction in complete, production-quality code**—do not dump a long prose strategy brief, persona essay, or unstyled wireframe, and never default unrelated categories to a utilitarian SaaS pricing table. Output a standalone written brief or critique *only* when the user explicitly asks for strategy, planning, or review without implementation.

# Design thinking

Use when a request starts with a vague goal such as 'make onboarding better' or asks for a new experience. Read [strategy](../../knowledge/strategy.md) and [category directions](../../knowledge/category-directions.md); use [improvement loop](../../knowledge/improvement-loop.md) when revising an existing design.

1. Extract known audience, task, context, business objective, constraints and existing evidence from the request and repository. Label assumptions; ask only for missing facts that would materially change the direction.
2. Write a one-sentence problem statement with a user, need, action and desired result. Map entry → decision → action → outcome; mark friction and required information.
3. Generate two different structural solutions when feasible, not two skins. Compare task clarity, implementation cost, accessibility and risks; choose one and state why.
4. Identify the least expensive way to test the riskiest assumption and define a success signal plus guardrails. Choose motion, sound, scroll effects or 3D only after the task and content justify them; quiet, native behavior is the default.

Example: For confusing pricing, compare a side-by-side limits table with a guided recommendation, rather than immediately recoloring cards. Deliver a brief containing problem, evidence vs assumptions, selected direction, rejected alternative, and validation plan. Do not claim interviews or user validation you did not conduct.
